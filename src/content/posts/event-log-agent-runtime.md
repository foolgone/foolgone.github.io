Agent 跑长任务时，最烦的不是模型答错，而是「跑到一半进程没了」。重启之后你得回答三个问题：刚才做到哪了？哪些工具调用已经产生副作用？重试会不会重复执行？

如果状态存在一张可写的表里，这三个问题都很难答。这篇是我在 agent-runtime 里做的取舍。

## 可写状态表的问题

最直觉的设计是：会话表、消息表、工具调用表，每次变化 update 一下。它有三个绕不开的毛病。

**崩溃时状态是半写的。** 工具执行成功、状态还没落库，进程就没了。重启后系统认为这次调用没发生，于是重试一次——副作用就产生了两次。

**回答不了「为什么是现在这个状态」。** 表里只有结果，没有过程。用户问「你刚才为什么查了三次库存」，你只能猜。

**并发和顺序靠人记。** 哪些字段可以并发改、哪些必须串行，全靠约定，而约定总会破。

## 换成事件日志

核心思路只有一句：**会话状态不是存出来的，是重放出来的。**

每一次状态变化都追加一条事件，不允许修改和删除：

```
user/message    用户输入
model/message   模型回复
tool/call       决定调用某工具（先写，后执行）
tool/result     工具返回
tool/error      工具失败
```

当前状态 = 从第一条事件重放到最后一条的结果。没有可写状态表，只有一个 append-only 的日志。

好处立刻出现：

- 崩溃恢复不需要额外机制，进程没了日志还在，重放一遍就回到崩溃前的位置
- 「为什么是这个状态」有了答案，就是这条事件流
- 并发问题退化成「追加顺序」，而追加顺序是存储层能保证的

## 先记账，后执行

事件日志解决不了副作用重复，还需要一条规则：**工具调用在执行之前就先写 `tool/call`。**

于是崩溃时只有两种可能：

- 日志里有 `tool/call`，没有 result → 已受理，结果未知
- 日志里没有 `tool/call` → 确定没执行过

第一种情况不能自动重试，要交给上层决定：是查幂等键确认，还是让用户重新确认。关键是系统**知道**自己不知道，而不是当作没发生。

界面上那张一直停在「执行中」的卡片，就是这条规则的可见结果：它如实说出是哪一次调用，而不是笼统地报一句「出错了」。

## 权限在装配期定死

Agent 的工具权限如果放在运行期判断，每个调用点都要记得判断，忘一处就是漏洞。

更稳的做法是把工具注册表「收窄」：根据当前会话的授权，生成一个只包含允许项的新注册表。之后的取用、schema 生成、执行全都只看这个收窄后的集合，运行期不再做权限判断。

这样权限问题从「每处都要小心」变成「只有一个地方能出错」。

## 代价

事件日志不是免费的：

- **日志会一直长。** 长会话需要快照，快照本身又要保证和日志一致
- **重放有成本。** 每次恢复都要从头读，所以要定期做检查点
- **事件格式会变。** 上线半年后字段一定会改，需要版本号和向后兼容的重放逻辑
- **调试方式变了。** 不能直接改数据库「修一下」，只能追加一条修正事件

最后一条最需要适应。它逼你把每一次「手工修复」都变成可追溯的操作，短期麻烦，长期省事。

## 结论

把状态建模成事件流，本质上是在换一个问题：从「怎么保证状态写对」换成「怎么保证事件追加对」。

后者简单得多——追加是单一操作，而「写对」需要处理并发、部分失败和顺序。

如果你的 Agent 会跨多次请求运行，值得认真考虑这件事。
