做 RAG 的团队常有一个共同反应：效果不好，先换模型，再改 prompt。但把一次问答拆开看，模型只负责最后一步——它拿到的上下文，已经决定了答案的上限。

> 检索错了，再强的模型也只能一本正经地编。

下面是我在客服知识库这类场景里反复验证过的几个判断。

## 先把链路拆开

一次 RAG 请求至少有四段：切分、召回、重排、生成。

线上出问题时，先判断错在哪一段，再决定改什么。方法很简单：把最终答案依赖的那段原文，手动塞进上下文，看模型能不能答对。

- 能答对 → 问题在检索，别动 prompt
- 还是答错 → 问题在生成或指令，检索是背锅的

这一步能省掉大量无效调参。

## 切分：块是检索的最小单位，也是最大的坑

固定字数切分最省事，也最容易出问题。它会把一张表格切成两半，把「如上所述」留在没有上下文的块里。

我现在的做法是：

- 先按文档结构切（标题、段落、表格、列表），再按长度合并，不做硬切
- 每个块带上标题路径，比如 `产品手册 > 退款政策 > 时效`，命中后模型知道这段属于哪
- 表格整块保留，不拆
- 重叠窗口 10%–15% 足够，再多只会让召回结果重复

标题路径看起来是小优化，实际收益很大：同一个「7 个工作日」出现在退款和换货两个章节里，没有路径就分不清。

## 召回：混合检索几乎总是优于单一向量

向量检索擅长语义相近，不擅长精确匹配：型号、订单号、专有名词、数字。BM25 恰好相反。

中文场景还有一层：分词器直接决定召回率。业务里如果大量出现产品型号、简称、错别字，按字级别的 n-gram 往往比分词更稳，代价是索引变大。

融合两种结果时，RRF（倒数排名融合）比手动调权重省心：

```python
def rrf(rank_lists, k=60):
    scores = {}
    for ranks in rank_lists:
        for position, doc_id in enumerate(ranks, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + position)
    return sorted(scores, key=scores.get, reverse=True)
```

top-k 也不是越大越好。候选变多，重排的负担和噪声一起上来。先召回 50 条再重排到 5 条，通常比直接召回 20 条更好。

## 重排：决定「能不能用」

召回负责「不漏」，重排负责「排序」。两者目标不同，所以需要两套模型。

- 召回用双塔或 BM25，追求快
- 重排用 cross-encoder，把 query 和候选拼在一起打分，追求准

重排还有一个常被忽略的作用：给出一个可信度分数。分数低于阈值时直接拒答，比让模型硬答安全得多。

## 拒答是必须设计的出口

很多 RAG 系统没有「不知道」这个状态。检索没命中，也照样把 top-1 塞给模型，于是模型只能编。

我的做法是把拒答写进链路：

1. 重排最高分低于阈值 → 直接返回「没有找到相关内容」
2. 检索命中了但相互矛盾 → 把矛盾点列出来，让用户判断
3. 问题超出知识库范围 → 引导到人工

第三条在客服场景尤其重要。答错一次的代价，远高于说一句「我帮你转人工」。

## 评测：没有量测就没有优化

改切分、换分词、调阈值，每一步都该有数字支撑，否则就是凭感觉搬家。

最小可用的评测集只需要几十条：

- 每条包含问题、期望答案，以及答案应来自哪个文档
- 分别统计「检索命中率」和「答案正确率」
- 两个指标一起看：检索命中但答错，说明是生成问题；检索没命中，后面都不用看

这套东西搭起来不超过一天，但能让后面所有的调整变得可比较。

## 结论

RAG 不是「把文档丢进向量库」这么一件事。它是一条有四个环节的链路，每一环都有自己的失败模式。

如果只能记住一句话：**先确认错在哪一段，再改那一段**。大部分时候，需要改的不是 prompt。
